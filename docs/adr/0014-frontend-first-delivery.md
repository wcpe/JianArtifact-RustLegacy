# ADR-0014：前端先行交付工序与契约骨架

## 状态
已接受

## 背景
- 管理端 Web 体验需要在后端业务成型前先固化：页面流程、组件与交互的反复打磨成本远低于后端业务返工，第一期希望 UI 验收尽早发生。
- ADR-0012 已确立 utoipa 从后端 Rust 代码生成的 OpenAPI 为管理 API 契约唯一真源，`apps/devmock` 契约必须与其自动比对、零漂移。
- 若直接"前端先行"，前端与 devmock 开发所依赖的契约无处可来：手写契约草案会与真源脱节形成漂移窗口，等后端业务实现则前端被完全阻塞。需要一个既不动摇 ADR-0012 真源、又能让前端先开工的交付工序。

## 决策
M1 采用「前端/mock 先行、后端业务后行」的交付工序，与 ADR-0012 以**契约骨架先行**方式调和。每个域（认证、用户、仓库与 ACL、Token、浏览、迁移等）开工时按三步推进：

1. **契约骨架先行**：后端先落 axum handler 空实现，utoipa 注解齐全——请求/响应模型完整声明，handler 只返回「未实现」的占位响应，不写业务逻辑；由此生成该域的 OpenAPI。
2. **前端与 devmock 对契约开发**：`apps/web` 的 API 类型由该 OpenAPI 生成，`apps/devmock` 场景与该 OpenAPI 自动比对，两者并行开发。
3. **后端业务实现最后补齐**：在既有骨架内填入业务逻辑，必须通过既有契约比对，OpenAPI 不因实现而漂移。

约束：

- 契约骨架合入即视为**契约冻结草案**：此后修改契约必须在同一变更内同步前端与 devmock，不允许单方修改。
- ADR-0012 不被取代：契约唯一真源仍是 utoipa 从后端代码生成的 OpenAPI，本决策只是把「生成真源的代码」提前到业务实现之前落地。

## 理由
- 契约始终从后端代码生成，devmock 的比对基准与最终实现同源，零漂移由机器保证，完整延续 ADR-0012 的机制。
- 前端不被后端业务进度阻塞，管理端体验与 UI 验收可以提前完成。
- 契约在骨架阶段就被前端与 devmock 双方消费检验，接口设计问题在业务实现之前暴露，此时修正成本最低。

## 后果
- 正面：契约零漂移；前端与后端业务实现解耦并行；UI 验收提前，管理端体验先行固化。
- 代价与约束：
  - 每个域后端至少两次提交：契约骨架一次、业务实现一次。
  - 骨架期管理端真连后端只会得到「未实现」响应，该阶段的演示与前端开发必须由 devmock 承担。

## 备选方案
- **前端按手写契约草案先行**：草案与最终 utoipa 生成的契约之间存在漂移窗口，后端落地时前端与 devmock 需要对账返工，违背零漂移目标——否。
- **改为 design-first 手写 OpenAPI（取代 ADR-0012）**：手写 OpenAPI 为真源、后端实现向其对齐，需要额外一层「实现与手写契约一致性」检查，且推翻已被验证有效的代码生成防漂移机制——否。
