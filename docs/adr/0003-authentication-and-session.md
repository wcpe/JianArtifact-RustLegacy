# ADR-0003：认证与会话方案

## 状态
已接受

## 背景
第一期要求完整本地认证：用户名密码登录、有明确 TTL 且可刷新的 Web 会话、退出即时失效、API Token 签发与吊销、适配 CLI 的鉴权方式。同时数据库与日志中不得出现任何明文凭据，被禁用用户与被吊销凭据的下一次请求必须立即失败。

## 决策
- 密码使用 Argon2（内存安全参数）哈希存储。
- Web 会话使用 JWT（HS256 签名）；服务端持有可查询的撤销状态，退出提交成功后，下一次携带该会话的请求必定失败，且不影响同一用户的其他会话与 API Token。
- JWT 撤销表只存**域分隔哈希**（对令牌标识加域前缀后哈希），不存原始令牌或可逆形式。
- API Token：明文只在签发时显示一次，持久化只存哈希；可列出元数据、可吊销。
- CLI 场景支持 Basic Auth（用户名 + 密码或 API Token）与 Bearer；携带凭据但校验失败的请求必须以 401 拒绝，不得回退为匿名或任何已认证身份。
- 每个受保护请求均校验用户启用状态，禁用生效后下一次请求必定失败。

## 理由
- JWT 自包含声明减少每请求的会话查询负担；撤销状态表补足 JWT 天然缺失的「退出即时失效」能力，两者组合沿用已验证的设计。
- 撤销表与 Token 均只存哈希，数据库泄露不等于凭据泄露；域分隔前缀防止不同用途的哈希值被互换滥用。
- HS256 对称签名对单服务自签自验足够；无跨服务验签需求时引入非对称密钥只增加密钥管理负担。

## 后果
- 正面：认证矩阵（匿名/用户/Admin × 会话/Token/Basic）可穷举测试；「吊销后下一次请求必定失败」成为可验收断言。
- 负面与约束：受保护请求需附带一次撤销状态与用户状态查询，需保证该查询轻量；HS256 密钥属机密配置，泄露即可伪造会话，密钥不得入库、不得进日志（受敏感信息扫描门禁约束）。

## 备选方案
- 不透明会话表（随机 ID 查库）：撤销天然即时，但无法携带声明，且每请求必查库；在同样需要状态查询的前提下，JWT 声明携带更省。
- Cookie 会话：对 Maven/npm/curl 等 CLI 客户端不友好，且引入 CSRF 防护面；统一 Bearer 使管理端与 CLI 鉴权模型一致。
- RS256 非对称签名：仅在多方独立验签时有价值，单体服务下密钥管理复杂度不成比例。
