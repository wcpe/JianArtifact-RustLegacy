# ADR-0042：单一通用出站代理（取代三键代理配置）

## 状态

已接受（取代 ADR-0024 中「`http` / `https` 保留为 scheme 专属代理、新增 `all` 键三键并存」的决策；ADR-0020 的共享出站客户端 / 配置真源 / 凭据脱敏、ADR-0022 的运行时热替换、ADR-0024 的「用户名回显、密码三态不回显」与 SOCKS5 支持、ADR-0030 的凭据加密落库均沿用）

## 背景

ADR-0024 落地后 `[network.proxy]` 有 `http` / `https` / `all` 三键，设置页相应有三个代理槽位（各带 URL / 用户名 / 密码 / 测试 / 清除）。真机运维暴露的问题：

1. **心智负担与误配**：三个槽位让"配一个代理全局走"这一压倒性主流场景变复杂——用户三个都填、或填错槽位，排障时无从判断哪一份生效。
2. **实际需求单一**：受限网络部署几乎总是"一个企业出口代理"，scheme 分流（http 走 A、https 走 B）从未被使用，属为不存在的场景保留的复杂度。

约束不变：rustls-only、单一二进制；凭据不入库明文、不进日志、不回显；简单优先。

## 决策

1. **`[network.proxy]` 收敛为单键 `url`**（env `JIANARTIFACT_NETWORK_PROXY_URL`）+ 既有 `no_proxy`。接受 `http://` / `https://` / `socks5://` / `socks5h://` 前缀（用户自填 scheme），经 `reqwest::Proxy::all(url)` 注入为全 scheme 代理；其余 scheme 给中文校验错误拒绝。
2. **旧键自动映射 + WARN 废弃**：TOML / env 中旧 `http` / `https` / `all` 任一给值且 `url` 未给时，按优先级 **`all > https > http`** 折叠为 `url` 并打启动 WARN（提示改用 `url` 键）；`url` 与旧键同时给值时 `url` 为准、WARN 旧键被忽略。升级不炸、行为可预期。
3. **凭据模型不变**：网页仍为 URL + 用户名 + 密码三字段（密码三态：缺省保留 / 空串清空 / 非空设置，绝不回显）；加密落库（ADR-0030）收敛为单代理项，旧三项落库 JSON 读取时按同一优先级折叠、凭据不丢，新写入只写单项。
4. **API 契约收敛**：`GET`/`PATCH /api/v1/settings` 的 `network_proxy` 从 `{http,https,all,no_proxy}` 收敛为 `{proxy,no_proxy}`。不为旧三键提供 PATCH 兼容（前端与后端同二进制发布，无旧新组合；外部脚本属破坏性变更，记 CHANGELOG）。

## 理由

- **单键贴合真实用法**：全部已知部署都是"一个代理全局走"，`Proxy::all` 一键覆盖 http+https+socks，正是 ADR-0024 里 `all` 键的既有语义——收敛等于把事实上的用法固化为唯一路径。
- **用户自填 scheme 而非拆键**：`socks5://` 与 `http://` 代理的差异已由 URL scheme 表达，无须用配置键区分；也天然支持 `socks5h://`（远端 DNS，受污染网络推荐）。
- **自动映射而非硬废弃**：已有部署（TOML / env / 加密落库）升级后无须手改配置即可继续工作，符合向后兼容默认；WARN 引导迁移，避免旧键无限期存活。
- **优先级 `all > https > http`**：`all` 本就是全 scheme 兜底、语义最接近新单键；`https` 次之（出站以 https 为主）；确定性规则可穷举测试。

## 后果

- 正面：配置面与设置页大幅简化（一个槽位）；排障时唯一生效代理一目了然；消除三键注入顺序的隐性复杂度。
- 负面 / 约束：失去 scheme 分流能力（http / https 走不同代理）——无真实需求，需要时另写 ADR 恢复；`GET`/`PATCH /settings` 契约破坏性变更（外部脚本需适配）。
- 仍不支持 SOCKS4 / 按 host 多代理路由表（沿用 ADR-0024 边界）。

## 备选方案

- **保留三键仅收敛前端**：后端留死代码与永久兼容负担，三键注入顺序复杂度仍在，落选。
- **硬废弃旧键（不映射，启动报错）**：升级即炸，违背向后兼容默认，落选。
- **维持现状**：真机已证实误配成本高于 scheme 分流的假想收益，落选。
