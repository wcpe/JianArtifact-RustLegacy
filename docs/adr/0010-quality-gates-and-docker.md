# ADR-0010：质量门禁与 Docker 化验证

## 状态
已接受

## 背景
需求把严格的格式检查、静态分析、测试门禁与架构边界检查列为已确认决策，并硬性要求构建、测试、lint、typecheck 与协议验收统一在 Docker 中执行，宿主项目目录不得生成 `target`、`node_modules` 或大型测试产物。若门禁清单与执行环境不在开工前钉死，质量标准会退化为口头约定。

## 决策
- **合并前硬门禁清单**（任一失败即阻断合并）：
  1. 格式检查（rustfmt --check、Prettier 只检查模式）。
  2. 编译/构建检查。
  3. 静态分析，警告视为失败（clippy 全 targets 全 features、ESLint --max-warnings 0）。
  4. 单元测试、集成测试与受影响的协议测试。
  5. API 与 devmock 契约一致性比对（见 ADR-0012）。
  6. 架构依赖方向检查（ui 不得依赖 web、协议层不得直连数据库等）。
  7. 敏感信息扫描。
  8. 依赖漏洞与许可证检查。
  9. 文档漂移检查：FR、API 或行为变化必须同步正式文档。
- **Docker 化执行**：构建、测试、lint、typecheck、协议验收统一在 Docker 中执行；宿主机不得直接运行 cargo/pnpm/npm 等构建测试命令；Rust `target`、前端 `node_modules`、包管理器缓存与测试产物一律使用 Docker volume 或容器临时目录，不写入宿主项目目录。
- 不创建 git worktree 作为并行开发或测试手段。
- CI 与本地使用**同一组脚本入口**，禁止 CI 单独维护另一套命令。

## 理由
- 同一组脚本 + 同一容器环境消除「本地通过、CI 失败」的环境漂移，静态分析与测试结果可复现。
- 宿主零产物保证仓库目录洁净，敏感信息扫描与全量检查不被海量构建产物拖垮。
- 门禁清单写入 ADR 使其成为不可协商的合并条件，任何放宽都必须走 ADR 变更。

## 后果
- 正面：质量标准机器化；任何人、任何机器上门禁行为一致；架构边界违规在合并前被阻断。
- 负面与约束：容器内首次构建较慢，需依赖缓存 volume 优化；开发者必须适应容器化工作流；门禁脚本本身成为需要维护与验收的工程资产。

## 备选方案
- 宿主直跑 + CI 兜底：工具链版本因人而异，静态分析与测试结果不可复现。
- 仅在 CI 执行门禁：反馈周期长，本地无法预验证，问题堆积到合并时爆发。
- 各子工程自定义门禁标准：同一仓库内质量标准不一致，架构级检查（依赖方向、契约比对）无处安放。
