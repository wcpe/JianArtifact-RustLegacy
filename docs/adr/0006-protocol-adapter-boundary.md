# ADR-0006：格式协议适配层边界

## 状态
已接受

## 背景
第一期实现 Raw/Maven/npm 三种格式协议，M2 起还将扩展 Docker/OCI、Cargo、PyPI、Go、NuGet 等格式。若各格式协议实现各自为政、直连存储，新增格式将扩散修改到所有分发点，且存储不变量（ADR-0002 的提交顺序）会被多处复制而失守。需求同时把「协议 handler 直接访问 SQLite」列为架构审查必须阻断项。

## 决策
- 所有格式协议实现统一的**格式协议抽象**，经 **Format 注册表**注册与分发：每种格式是注册表中的一个实现，路由按仓库的格式属性从注册表取实现。
- 协议适配层**禁止直接读写数据库**，必须通过领域服务与仓储接口完成一切读写；存储提交顺序、授权判定、覆盖策略均只在领域服务层实现一次。
- 禁止在通用代码中按格式名 if-else / switch 堆叠分支；出现新的按格式分支需求时，一律下沉为格式抽象上的方法。

## 理由
- 注册表 + 抽象接口使新增格式是「加一个实现并注册」，而非「修改所有分发点」，符合开闭原则，直接压低 M2 的扩展成本。
- 协议层与持久化解耦保证存储与授权不变量单点实现、单点测试；协议测试只需针对客户端可观察行为。
- 「协议层禁直连数据库」是可静态检查的依赖方向规则，能进入架构门禁（ADR-0010）自动阻断。

## 后果
- 正面：格式扩展成本线性；边界违规可被机器检查；三格式共享的通用能力（流式、校验、分页浏览）不重复实现。
- 负面与约束：抽象接口需容纳三格式差异（Maven checksum sidecar 与 release/snapshot 语义、npm packument 合并与 dist-tag、Raw 目录浏览），接口须在第一期三格式上磨合定型，避免过早固化；格式特有能力不得以「通用接口加格式开关」的方式泄漏回通用层。

## 备选方案
- 各格式 handler 直接操作存储：提交顺序与授权逻辑被复制多份，不变量必然逐渐失守。
- 通用层按格式名条件分支分发：每新增格式需要修改全部分支点，违反开闭原则，被需求明确禁止。
- 每格式独立微服务：单体、低运维定位下复杂度完全不成比例。
