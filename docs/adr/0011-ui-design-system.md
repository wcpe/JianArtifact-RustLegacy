# ADR-0011：UI 设计系统

## 状态
已接受

## 背景
管理端、共享组件库与预览站（apps/web、apps/ui、apps/wiki）需要统一的组件方案。需求要求共享设计系统分四层组织、覆盖键盘操作与焦点可见性等无障碍能力，产品页不得各自复制基础组件。上一代实现使用运行时组件库的经验表明：深度定制样式时常与库内置样式互相覆盖，且此类冲突在 jsdom 类测试环境中难以发现，设计令牌也受制于库的主题体系。

## 决策
- 采用 **shadcn/ui + Tailwind CSS**，以 **Radix Primitives** 为无障碍交互基底；明确**不使用 Mantine 等运行时组件库**。
- 组件源码按 shadcn/ui 模式直接归入 `apps/ui`，成为本仓库自有代码，而非 node_modules 中的运行时依赖。
- `apps/ui` 组件按四层组织：基础组件、复合组件、页面布局、业务模式；只允许被 `web` 与 `wiki` 单向依赖。
- 表格统一使用 **TanStack Table**（headless），样式与交互由 `apps/ui` 封装。
- 无障碍为硬要求：键盘操作、焦点可见性、语义标签、错误提示与基础响应式布局必须覆盖，并以 `apps/wiki` 预览站作为可访问性验收入口。

## 理由
- **组件源码自主权**：源码在本仓库内，样式与行为可任意修改，不被上游 breaking change 与发版节奏绑架，彻底消除「库内置样式覆盖自定义样式」一类冲突。
- **无障碍基底**：Radix 提供经过广泛验证的焦点管理、ARIA 语义与键盘交互，自研这些细节的成本与风险过高。
- **设计令牌自主**：Tailwind 配置与设计令牌完全归项目所有，主题体系不依赖任何库的运行时主题机制。
- TanStack Table 是 headless 方案，与「样式自主」路线一致，可覆盖分页大表格等第一期场景。

## 后果
- 正面：组件可自由演进；无运行时组件库升级风险；无障碍验收有稳定基底与预览入口。
- 负面与约束：复制入仓库的组件需要自行维护与择机同步上游修复；新增共享组件必须先在 wiki 建立可复现预览再进入产品页（M1-FR-036）；四层分层与「ui 不依赖 web」纳入架构门禁。

## 备选方案
- Mantine：上一代实现使用过的运行时组件库，功能全面，但样式覆盖机制与设计令牌受库约束，深度定制冲突已被实际经验证实。
- Ant Design：设计语言强绑定、主题定制成本高、运行时包体大，与设计令牌自主目标冲突。
- 完全自研组件：无障碍细节（焦点陷阱、ARIA、键盘导航）自研成本与出错风险不成比例。
