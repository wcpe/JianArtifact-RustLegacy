# ADR-0012：API 契约唯一真源

## 状态
已接受

## 背景
管理 API 同时被 `apps/web`（真实调用）、`apps/devmock`（契约模拟）与文档消费。需求明确要求 devmock 与真实后端 API 不得漂移，且门禁必须包含 API/Mock 契约一致性检查。若契约靠手写文档维护，三处（代码、文档、mock）各说各话只是时间问题。

## 决策
- 管理 API 契约以 **utoipa 从后端 Rust 代码生成的 OpenAPI 文档为唯一真源**：handler、请求/响应模型通过 utoipa 注解声明，OpenAPI 由代码构建产出。
- 前端 TypeScript 类型由该 OpenAPI **自动生成**，`apps/web` 不手写 API 模型类型。
- `apps/devmock` 的契约测试**自动与该 OpenAPI 比对**，请求/响应结构不一致即失败。
- 上述比对纳入合并前硬门禁（ADR-0010 第 5 项）；`docs/API.md` 只记录跨端点的稳定约定，不重复端点明细。

## 理由
- 代码生成保证文档与实现零漂移：handler 或模型一变，OpenAPI 必变，下游比对立即暴露不一致。
- 前端类型与 devmock 对同一真源自动比对，「mock 通过、真实后端失败」类缺陷在合并前被拦截。
- 单一真源避免同一契约在代码、文档、mock 三处重复维护；沿用已验证的设计，该机制在上一代实现中已证明能有效防漂移。

## 后果
- 正面：契约漂移被机器阻断而非靠评审发现；前端获得端到端的类型安全。
- 负面与约束：后端必须为每个对外端点维护 utoipa 注解，注解质量即契约质量，缺注解的端点视为契约缺失；OpenAPI 生成物是前端类型与 devmock 比对的输入，构建编排上后端契约产出必须先于前端类型生成（由 Turborepo 任务依赖表达）。

## 备选方案
- design-first 手写 OpenAPI YAML：契约与实现靠自觉同步，漂移只能靠人工评审发现，与「机器阻断漂移」的目标相悖。
- 手写 API 文档 + 人工比对：维护成本最高、可靠性最低，上一代经验表明必然漂移。
- 无契约、前端手写类型：类型安全形同虚设，devmock 无比对基准。
